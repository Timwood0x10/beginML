## 1. The formula: Agent = LLM + Context + Tools

The book's formula is almost elegant in its simplicity:

**Agent = LLM + Context + Tools**

goagent's practice fits squarely inside it, but adds the engineering key
word: **Harness**. The model stays fixed; what changes is the shell around
it — how context is organized, how tools connect, how failures are caught.
The book says "Harness engineering is the real competitive edge," and
goagent's six-layer architecture (LLM client → memory → tools → workflow →
security & observability → evolution) is a complete implementation of that
statement.

> **Fusion point**: theory gives coordinates, engineering gives answers.
> Every goagent layer maps to a "why" in the book.

## 2. Context engineering: the ceiling of capability

The book's chapter 2 claim: **context decides the Agent's capability
ceiling**. Model weights are static; what is visible in each request is
what is alive.

goagent counterparts:
- **LLM client layer** (`20-llm-client-layer.md`): multi-provider
  abstraction + failover — the engineering precondition for "context gets
  into the model reliably";
- **Retrieval system** (`10-retrieval-system-deep-dive.md`): hybrid search
  + scoring pipeline, answering "what should the model see" — the book warns
  "more is worse for LLMs," and goagent's **type-differentiated storage**
  (vector, full-text, structured each doing its own job) reduces
  hallucination, implementing exactly that principle.

> **Fusion point**: context engineering = ① fit it in (KV-cache friendly,
> window management) ② fit the right things (retrieval / memory filtering)
> ③ keep it stable (provider failover).

## 3. Memory: from "remembering" to "distillation"

The book's chapter 3 covers user memory and knowledge bases (short-term
context / long-term store / RAG pipelines).

goagent's **memory distillation** (`03-memory-distillation-deep-dive.md`)
goes one step further: a three-tier memory architecture (Session
short-term → Task execution log → Distilled experience), and answers a
question the book only touches — **memory is not about storing more, it is
about forgetting well**. The article opens with a failed word-frequency
experiment: high frequency ≠ importance; naive statistics lose semantic
structure; memory must be distilled into searchable, reusable experience.

> **Fusion point**: the value of memory is not storage but **distillation**.
> Short-term keeps context, mid-term keeps process, long-term keeps
> experience.

## 4. Tools: four paths and one safety net

The book's chapter 4 classifies tools into perception / execution /
collaboration, and spends time on the MCP ecosystem.

goagent's tool invocation layer (`05-tool-system-deep-dive.md`) gives a
more engineering-minded answer: **four invocation paths + one safety net**.
- Path 1: LLM-driven `tool_calls` (the book's native tool calling);
- Path 2: capability-planner semantic dispatch (a deterministic fallback
  when the LLM is unreliable);
- Path 3: ToolNode inside a workflow graph;
- Path 4: **MCP external tools** (`15-mcp-integration-deep-dive.md`:
  JSON-RPC 2.0, Stdio/SSE transports, automatic server discovery).

> **Fusion point**: the book's taxonomy answers "what tools are"; goagent's
> four paths answer "how to invoke tools reliably" — the real production
> question.

## 5. Planning & workflow: from ReAct to DAG

The book's chapter 1 treats ReAct as the baseline pattern. goagent's
workflow engine (`04-workflow-engine-deep-dive.md`) shows the engineering
upgrade of ReAct: a **config-driven DAG executor** — concurrent dispatch,
exponential-backoff retries, human-in-the-loop intervention, and MutableDAG
runtime topology changes.

> **Fusion point**: ReAct is the idea, DAG is the implementation. A
> production Agent needs "think-act-observe" turned into an orchestratable,
> interruptible, retryable graph.

## 6. Evaluation: turning "feeling" into signal

The book's chapter 6 stresses that evaluation turns performance into a
comparable signal — metrics, automated environments, statistical
significance.

goagent's evaluation framework (`21-evaluation-framework.md`) is a
three-layer design: test cases → evaluators (LLM judge / dimension judge) →
runner & comparison. **Evaluation is not the endpoint but the input to
evolution** — goagent wires it directly into the evolution system.

> **Fusion point**: without evaluation, evolution is a blind box. You need
> comparable signals before you can get "stronger" with direction.

## 7. Evolution: mutation + selection + inheritance

The book's chapter 8 covers continuous evolution (knowledge / instruction /
program / parameter), chapter 7 model post-training (SFT, RL).

goagent's autonomous evolution (`11-autonomous-evolution-deep-dive.md`,
`24.1-ga-deep-dive.md`) delivers a no-model-training evolution:
**evolution = mutation + selection + inheritance** — GA population,
TieredScorer three-tier scoring, Promoter champion/challenger promotion,
genealogy records. It is a concrete implementation of the book's "obtain
learning signals from trajectories": evolution drives prompt/strategy
improvement from evaluation signals instead of touching model weights.

> **Fusion point**: post-training changes the model (slow path); strategy
> evolution changes behavior (fast path). Start with the fast path in
> production.

## 8. Multi-agent: collaboration and failure modes

The book's chapter 10 gives a taxonomy of multi-agent collaboration and
frankly states **multi-agent is not always better than single-agent**, with
failure modes listed.

goagent's counterpart is the Agent Harmony Protocol
(`02-agent-harmony-protocol.md`) — communication protocol first, so
collaboration has a common language.

> **Fusion point**: ask "is a single agent enough" before collaborating;
> when collaborating, settle the protocol first, then the division of labor.

## 9. Summary in one paragraph

The book gave the formula and direction; goagent gave the engineering
answers. The most pragmatic path to building your own Agent:

1. **Context**: manage "what the model sees" (retrieval + memory
   distillation);
2. **Tools**: guarantee "reliable invocation" (four paths + MCP + fallback);
3. **Evaluation**: turn results into signals;
4. **Evolution**: use signals to iterate strategies;
5. Multi-agent is complexity to add last, if ever.
