# Agent 构建精要：goagent 工程实践 × AI Agent 理论

> 本文是 **融合改写笔记**，不是原文搬运：
> - 工程实践部分基于本人原创的 goagent（ares 框架）系列文章（本目录 00–24.1 各篇）；
> - 理论框架部分参考《深入理解 AI Agent》（bojieli/ai-agent-book，[Apache License 2.0](https://github.com/bojieli/ai-agent-book/blob/main/LICENSE)）的章节脉络；
> - 写作方式：以 goagent 的真实工程事实为骨架，用书中概念做坐标系，只保留双方真正有价值的部分。

## 一、总纲：Agent = LLM + 上下文 + 工具

书里的公式简洁得近乎优雅：

**Agent = LLM + 上下文 + 工具**

goagent 的实践完全落在这个公式上，但补上了工程侧的关键词：**Harness（套件）**。模型本身不变，变的是外面那层壳——上下文怎么组织、工具怎么接入、失败怎么兜底。书里说"Harness 工程才是竞争力"，goagent 的六层架构（LLM 客户端 → 记忆 → 工具 → 工作流 → 安全可观测 → 进化）就是这句话的完整注脚。

> **融合要点**：理论给坐标，工程给答案。看 goagent 每一层，都能在书里找到它对应的"为什么"。

## 二、上下文工程：决定能力上限

书中第 2 章的核心论断：**上下文决定 Agent 的能力上限**。模型参数是死的，每次请求能看到的上下文才是活的。

goagent 的对应实践：
- **LLM 客户端层**（`20-llm-client-layer.md`）：多 Provider 抽象 + failover，本质是保证"上下文能稳定送进模型"这一工程前提；
- **检索系统**（`10-retrieval-system-deep-dive.md`）：混合搜索 + 评分管线，解决"该给模型看什么"——书中警告"对 LLM 来说，越多越糟糕"，goagent 用**数据类型分流**（向量库、全文索引、结构化存储各管一摊）降低幻觉，正是这一原则的实现。

> **融合要点**：上下文工程 = ① 装得下（KV Cache 友好、窗口管理）② 装得对（检索/记忆筛选）③ 装得稳（Provider failover）。

## 三、记忆：从"记住"到"蒸馏"

书中第 3 章讲用户记忆与知识库（短期上下文 / 长期存储 / RAG 管道）。

goagent 的**记忆蒸馏**（`03-memory-distillation-deep-dive.md`）走得更远一步：三层记忆架构（Session 短期 → Task 执行日志 → Distilled 经验提炼），并明确回答了一个书中只点到的问题——**记忆不是越多越好，要会遗忘**。文章开头用词频分析的失败案例说明：高频 ≠ 重要，朴素统计会丢失语义结构，必须蒸馏成可检索、可复用的经验。

> **融合要点**：记忆的价值不在存储，在**提炼**。短期保上下文、中期保过程、长期保经验。

## 四、工具：四条路径与一个兜底

书中第 4 章把工具分成感知 / 执行 / 协作三类，并花了篇幅讲 MCP 生态。

goagent 的工具调用层（`05-tool-system-deep-dive.md`）给出了一个更工程化的答案：**四条调用路径 + 一个兜底**。
- 路径一：LLM 驱动的 `tool_calls`（书中"原生工具调用"）；
- 路径二：Planner 语义分析兜底调度（LLM 不靠谱时的确定性引擎）；
- 路径三：Workflow Graph 中的 ToolNode；
- 路径四：**MCP 外部工具**（`15-mcp-integration-deep-dive.md`：JSON-RPC 2.0、Stdio/SSE 双传输、服务自动发现）。

> **融合要点**：书的分类回答"工具是什么"，goagent 的四路径回答"工具怎么被可靠地调起来"——后者才是生产环境的真问题。

## 五、规划与工作流：从 ReAct 到 DAG

书中第 1 章把 ReAct 作为基础模式。goagent 的工作流引擎（`04-workflow-engine-deep-dive.md`）展示了 ReAct 的工程化升级：**配置驱动的 DAG 执行器**——并发调度、指数退避重试、Human-in-the-Loop 人为干预、MutableDAG 运行时拓扑变更。

> **融合要点**：ReAct 是思想，DAG 是实现。生产级 Agent 需要把"思考-行动-观察"变成可编排、可干预、可重试的图。

## 六、评估：把"感觉"变成信号

书中第 6 章强调：评估是把表现变成可比较信号的前提，涉及指标体系、自动评估环境、统计显著性。

goagent 的评估框架（`21-evaluation-framework.md`）是三层设计：测试用例层 → 评估器层（含 LLM judge / 维度 judge）→ Runner 与比较层。**评估不是终点而是进化的输入**——goagent 把它直接接进了进化系统。

> **融合要点**：没有评估，进化就是盲盒。先有可比较的信号，才有"变强"的方向。

## 七、进化：变异 + 选择 + 遗传

书中第 8 章讲持续进化（知识 / 指令 / 程序 / 参数四层更新），第 7 章讲模型后训练（SFT、RL）。

goagent 的自主进化（`11-autonomous-evolution-deep-dive.md`、`24.1-ga-deep-dive.md`）给出了一个"不训练模型"的进化实现：**进化 = 变异 + 选择 + 遗传**——GA 种群、TieredScorer 三层评分、Promoter 冠军/挑战者晋升、谱系记录。这是书中"从运行轨迹中获得学习信号"的一种具体落地：用评估信号驱动 prompt/策略的演化，而非动模型参数。

> **融合要点**：后训练改模型是慢路径，策略进化是快路径。生产环境先从快路径做起。

## 八、多智能体：协作与失败模式

书中第 10 章给出多 Agent 协作的分类框架，并直言**多 Agent 并非总是优于单 Agent**，还列出了失败模式。

goagent 侧的对应是 Agent Harmony Protocol（`02-agent-harmony-protocol.md`，多智能体通信基石）——通信协议先行，协作才有共同语言。

> **融合要点**：先问"单 Agent 够不够"，再谈协作；真要协作，先定协议，再谈分工。

## 九、一句话总结

书给了公式与方向，goagent 给了工程答案。构建自己的 Agent，最务实的路径是：

1. **上下文**管好"模型看什么"（检索 + 记忆蒸馏）；
2. **工具**保证"可靠地调起来"（四路径 + MCP + 兜底）；
3. **评估**把效果变成信号；
4. **进化**用信号驱动策略迭代；
5. 多智能体是最后才考虑的复杂度。
